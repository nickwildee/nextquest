# NextQuest 리뷰 분석 정책

## 목적

리뷰 분석은 Steam의 전체 평가를 다시 요약하는 작업이 아니다. 후보 게임에서 반복되는 구체적인 플레이 특성을 찾고, 사용자가 과거 게임에서 입력한 취향과 비교할 수 있는 검증 가능한 근거를 만드는 작업이다.

내부 프로토타입은 미리 수집·분석·검수한 fixture를 사용한다. 사용자 요청 시 LLM을 호출하지 않는다.

## 근거 원칙

- 정상 사용자 흐름의 모든 분석 결과는 실제 리뷰 원문에서 가져온 문장을 근거로 사용한다.
- LLM은 근거 문장을 새로 만들거나 원문의 표현을 근거인 것처럼 바꾸지 않는다.
- LLM은 `sentenceId` 또는 원문 범위만 반환하고, 프로그램이 저장된 원문에서 해당 구간을 잘라 근거를 만든다.
- 같은 리뷰의 여러 문장이 같은 특성을 말해도 독립 의견 한 개로 센다.
- 리뷰 작성자의 긍정·부정은 게임의 특성에 대한 리뷰 의견이다. 사용자의 개인 취향 방향은 과거 게임의 하위 특성에 직접 입력한 `좋았음`과 `아쉬웠음`이 결정한다.
- 실제 리뷰 근거를 저장소에 포함하려면 작성자 식별자를 제거하고 최소 문장, 출처, 수집 시점과 이용 조건을 검수한다.
- 오류, 빈 결과와 충돌 상태를 테스트하는 합성 fixture를 실제 리뷰 근거처럼 사용자에게 제시하지 않는다.

## 분석 단위

리뷰 문장은 다음 세 수준으로 분류한다.

| 수준 | 의미 | 예시 | 개인화 근거 사용 |
| --- | --- | --- | --- |
| `generic_overall` | 게임 전체에 대한 짧은 감상만 있음 | `갓겜`, `노잼`, `개쓰레기겜` | 사용하지 않음 |
| `dimension_only` | 상위 경험 영역은 언급하지만 이유나 특성이 없음 | `전투가 재밌다`, `보스가 별로다` | 직접 근거로 사용하지 않음 |
| `trait_specific` | 구체적인 플레이 특성과 평가가 있음 | `공격 후딜이 길어서 회피가 답답하다` | 사용함 |

글자 수만으로 제거하지 않는다. `타격감 개좋음`, `노가다가 너무 심함`처럼 짧아도 구체적인 특성을 가진 문장은 유효할 수 있다.

## 특성 분류표와 키워드

각 상위 경험 영역마다 통제된 하위 특성 분류표를 둔다. 각 특성은 안정적인 ID, 설명, 동의어와 긍정·부정 예시를 가진다. 아래 분류는 구조를 설명하기 위한 예시이며 상위 영역의 최종 개수·명칭과 전체 하위 특성 목록은 구현 전에 확정한다.

```text
전투
├── impact_weight       타격의 무게감과 충격감
├── combat_pace         전투 속도
├── hitbox_quality      공격 판정
└── enemy_variety       적 종류와 전투 방식

조작
├── input_responsiveness 입력 반응성
├── animation_lock       행동 중 조작 제한
└── camera_control       카메라 조작
```

`타격감`, `손맛`, `묵직함`, `육중함`, `충격감` 같은 표현 목록은 다음 용도로만 사용한다.

- 명백한 후보 문장을 빠르게 표시한다.
- LLM에 특성의 의미와 게이머 표현 예시를 제공한다.
- 누락과 오분류를 사람이 검색하고 검수한다.

키워드 포함 여부를 수집·제외의 최종 조건으로 사용하지 않는다. `버튼을 눌러도 한 박자 뒤에 나간다`처럼 정해진 단어 없이 입력 반응성을 설명하는 문장을 놓칠 수 있기 때문이다.

분류표에 없는 구체적인 특성은 `other`와 제안 이름으로 반환한다. 여러 독립 리뷰에서 반복된 `other`만 사람이 검수해 정식 특성으로 승격한다.

## LLM과 프로그램의 책임

### LLM이 담당하는 일

- 문장의 상위 경험 영역 관련성 판별
- `generic_overall`, `dimension_only`, `trait_specific` 구분
- 통제된 특성 ID로 의미 정규화
- 긍정, 부정, 혼합 의견 분류
- 한 문장에 섞인 서로 다른 주장을 개별 claim으로 분리
- 애매함과 신뢰도 표시
- 최종 선택된 영어 근거의 한국어 번역

### 프로그램이 담당하는 일

- 리뷰와 문장 ID 부여
- 원문 범위로 근거 문장 추출
- 동일 리뷰 중복 제거
- 서로 다른 리뷰 수, 비율과 사용자 취향 계산
- 표본 범위와 의견 수 표시
- 근거 선택 개수와 다양성 제한
- 캐시, 버전, 비용 상한과 재시도 통제
- 근거 부족 시 `판단 불가` 처리

LLM은 중요도 점수, 개인화 결론과 노출 문장을 자유 형식으로 생성하지 않는다. 출력은 ID와 제한된 enum 중심의 구조화 데이터로 저장한다.

## 특성의 중요도와 의견 방향

구체적인 특성을 발견하는 일과 그 특성이 중요하다고 판단하는 일을 분리한다.

- **구체성**은 한 문장이 비교 가능한 플레이 특성을 설명하는지 나타낸다.
- **중요도**는 그 특성이 서로 다른 리뷰에서 얼마나 반복되는지 나타낸다.
- **의견 방향**은 특성을 언급한 리뷰 중 긍정·부정·혼합 의견의 분포다.

전체 리뷰 수가 아니라 해당 특성을 실제로 언급한 서로 다른 리뷰 수를 분모로 사용한다. 단순 과반만으로 `긍정 우세`나 `부정 우세`라고 표현하지 않고, 최소 표본과 신뢰 기준을 충족해야 한다. 화면에는 `최근 분석 리뷰 중 34/48개가 부정적으로 언급`처럼 분자와 분모를 함께 보여준다.

## 표본 구성

- Steam API의 `query_summary.total_reviews`, `total_positive`, `total_negative`로 요청 조건에 맞는 전체 모수를 기록한다.
- 분석한 리뷰 수와 조건에 맞는 전체 리뷰 수를 사용자에게 구분해 표시한다.
- 최근 리뷰의 실제 긍정·부정 비율을 인위적으로 50:50으로 바꾸지 않는다.
- 부족한 반대 의견을 찾기 위한 보충 표본은 대표 근거에 사용할 수 있지만 의견 비율 계산에서는 제외한다.
- 리뷰 100개는 전체 분석 목표가 아니라 한 번의 수집·분석 배치다.
- 배치별로 주요 특성 순위와 의견 분포의 변화를 계산하고, 충분히 안정된 뒤 수집을 멈춘다.
- 특정 상위 영역이나 하위 특성의 근거가 끝까지 부족하면 다른 영역의 충분한 근거로 덮지 않고 해당 특성을 `판단 불가`로 둔다.

게임당 분석 상한과 안정화 판정식은 실제 리뷰로 측정한 뒤 확정한다. 비용 보호를 위한 첫 검증값은 `100개 단위, 최대 500개`지만 제품의 확정 수치로 사용하지 않는다.

## 근거 선택과 노출

분석 결과와 화면에 보여주는 리뷰 수를 분리한다.

- 분석에는 안정화 기준까지 수집한 전체 유효 표본을 사용한다.
- 한 결과에는 대표 근거 3개를 기본으로 노출한다.
- 더보기로 최대 10개까지 노출한다.
- 가장 많이 반복된 의견의 일관성을 우선 보여준다.
- 같은 표현만 반복하지 않도록 의미가 다른 주요 특성, 긍정·부정과 조건부 의견을 함께 선택한다.
- 사용자가 같은 리뷰의 여러 문장을 독립적인 다수 의견으로 오해하지 않게 리뷰 단위로 중복을 제거한다.

## 언어와 번역

- 한국어 리뷰를 먼저 사용하고 근거가 부족한 상위 경험 영역과 하위 특성은 영어 리뷰로 보완한다.
- 다른 언어는 내부 프로토타입 범위에 포함하지 않는다.
- 영어 리뷰는 영어 원문으로 특성과 의견을 분석한다.
- 최종 근거로 선택된 문장만 별도 LLM 호출로 한국어 번역한다.
- 분석과 번역을 한 요청에서 수행하지 않는다.
- 번역에는 게임, 상위 경험 영역, 하위 특성 ID와 검수된 게이머 용어집을 함께 제공한다.
- 번역은 캐시하고 사람이 전부 검수한 뒤 노출한다.
- 화면에 한국어 번역과 영어 원문을 함께 제공하고 AI 번역임을 표시한다.
- 부정 표현, 은어, 줄임말과 욕설의 의미를 임의로 완화하지 않는다.

## Steam 태그 사용

Steam 태그는 게임 간 맥락 유사성을 보조하는 작은 가점으로만 사용한다.

- 내부 프로토타입은 수동으로 검수한 태그 fixture를 사용한다.
- 태그 유사성 가점에는 상한을 둔다.
- 태그가 다르거나 없다는 이유로 감점하지 않는다.
- 태그만으로 리뷰 특성이나 사용자의 취향을 판정하지 않는다.

공개 상점 응답에서 안정적으로 사용할 수 있는 태그 필드를 확인하지 못했으므로 실제 연동 전에는 수동 태그를 자동 수집으로 대체하지 않는다. 자세한 확인 내용은 [Steam API 계약](../technical/steam-api-contract.md)에 기록한다.

## 최신화 정책

### 내부 프로토타입

- 리뷰 스냅샷을 고정한다.
- 수집 시점, 요청 조건, 분류표·프롬프트 버전을 기록한다.
- 프로토타입 검증 중에는 같은 입력의 결과가 바뀌지 않게 자동 갱신하지 않는다.

### 실제 연동 이후

- 30일마다 새 리뷰와 수정된 리뷰가 있는지 확인한다.
- 기존 분석 표본의 20% 이상이 변경되거나 대규모 패치·DLC가 발생하면 갱신한다.
- 변경된 리뷰만 분석하고 성공한 기존 결과를 재사용한다.
- 수정된 리뷰는 원문 해시가 바뀐 경우 기존 claim을 교체한다.
- 대규모 패치가 플레이 특성을 바꾸면 패치 이후 리뷰로 새 분석 구간을 시작하고 영향을 받은 과거 특성을 현재 통계에서 제외한다.
- 분류표, 프롬프트 또는 출력 스키마가 바뀔 때만 필요한 범위를 전체 재분석한다.

패치 자동 감지는 초기 범위에 포함하지 않는다. 실제 연동 초기에는 검수자가 수동으로 갱신을 표시한다.

## 유료 LLM 호출 통제

- 사람이 먼저 실제 리뷰 20~30개를 문장 분리하고 정답 라벨을 만든다.
- 유료 호출 전에 입력·출력 토큰과 최대 비용을 계산해 사용자 승인을 받는다.
- 첫 평가는 소수 게임과 작은 배치로 실행하며 통과하기 전에는 확장하지 않는다.
- 첫 분석 후보는 [GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna)의 `medium` reasoning이다. 공식 문서는 Luna를 비용 민감·대량 작업용으로 설명하며 `medium`을 지원한다. 모델 지원 상태와 가격은 호출 직전에 다시 확인한다.
- 더 비싼 모델로 자동 승격하지 않는다.
- [GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra) 또는 [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol)은 사람 정답 평가에서 Luna가 통과하지 못하고 사용자가 별도 승인한 경우에만 제한적으로 비교한다.
- 요청은 리뷰 배치 단위로 분리하고 입력 내용 해시, 모델, 프롬프트, 분류표와 스키마 버전을 저장한다.
- 성공한 배치는 다시 보내지 않는다.
- 전송 또는 구조화 출력 실패만 최대 1회 재시도한다.
- 의미가 애매한 결과는 재호출하지 않고 사람 검수 대기열로 보낸다.
- 전체 예산과 배치별 비용 상한을 설정하고 초과하면 자동 중단한다.
- 출력은 설명문 없이 ID, enum, 신뢰도와 원문 범위 중심으로 제한한다.

## 구현 전에 검증할 수치

- 상위 경험 영역의 최종 개수·명칭과 영역별 하위 특성 분류표·동의어
- `other` 특성을 정식 특성으로 승격할 조건
- 배치 간 주요 특성이 안정됐다고 보는 변화 허용치
- 게임당 분석 상한
- 특성별 의견 우세를 표시할 최소 독립 리뷰 수와 신뢰 기준
- 한국어 우선 표본과 영어 보완 표본의 정확한 구성
- 대규모 패치에서 영향을 받은 특성을 구분하는 수동 검수 절차
