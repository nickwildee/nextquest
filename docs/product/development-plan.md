# NextQuest 개발 계획

## 개발 원칙

- 제품의 핵심 가치를 외부 연동보다 먼저 검증한다.
- YAGNI 원칙에 따라 현재 사용자 흐름에 필요하지 않은 기능을 미리 만들지 않는다.
- KISS 원칙에 따라 검수된 소수 게임과 단순한 상태 모델로 시작한다.
- DRY 원칙은 실제 중복이 확인될 때 적용하고, 예상만으로 추상화를 만들지 않는다.
- Steam, 리뷰 수집, AI 분석 문제를 한 번에 결합하지 않고 단계별로 교체한다.
- M0에서는 기술 스택, 데이터베이스, API, 세부 아키텍처를 고정하지 않는다.

## M0: 제품 정의 및 MVP 범위 확정

### 목적

구현 전에 해결할 문제, 대상 사용자, 핵심 가치, MVP 범위와 대표 사용자 흐름을 합의한다.

### 결과물

- `docs/project-context.md`
- `docs/product/scope.md`
- `docs/product/user-flow.md`
- `docs/product/development-plan.md`
- 핵심 문서로 연결되는 `README.md`

### 완료 조건

- 해결할 문제와 핵심 사용자를 한 문장으로 설명할 수 있다.
- MVP 포함 범위와 제외 범위가 구분되어 있다.
- 대표 사용자 흐름이 서비스 진입부터 구매 판단 저장까지 연결된다.
- 첫 개발 마일스톤의 우선순위와 완료 기준이 정의되어 있다.
- README에서 모든 핵심 문서로 이동할 수 있다.
- 문서 간 내용과 링크를 검증하고 사용자의 최종 확인을 받는다.

## M1: 개발 기반 구축

### 목적

M2의 대표 사용자 흐름을 외부 서비스 없이 안전하게 구현하고 반복 검증할 수 있도록 기술 스택, 프로젝트 구조와 개발 하네스를 확정한다.

### 기술 경계

- pnpm workspace 기반 모노레포에서 `apps/web`을 Next.js 애플리케이션으로 구성한다.
- 웹에 필요한 서버 기능은 Next.js Route Handler로 시작하며 M1에는 별도 API 애플리케이션을 만들지 않는다.
- `packages/domain`에는 프레임워크와 데이터베이스에 의존하지 않는 도메인 스키마, 규칙과 fixture를 둔다.
- 독립 실행·배포, 여러 클라이언트 또는 백그라운드 처리 요구가 확인되면 서버 기능을 별도 API 애플리케이션으로 분리한다.

### 검증 경계

- ESLint는 코드 품질, Prettier는 코드 형식, TypeScript strict 모드는 타입 검사를 책임진다.
- Zod로 fixture와 API 경계의 스키마를 검증하고 Jest로 도메인 규칙, golden fixture와 독립적인 Client Component를 테스트한다.
- Storybook과 MSW로 컴포넌트 상태를 재현하고 Storybook Vitest addon과 a11y addon으로 story 렌더링, 상호작용과 접근성을 검증한다.
- Playwright는 대표 사용자 흐름과 실패 trace, GitHub Actions는 PR의 공통 검증 실행을 책임진다.
- `*.test.ts(x)`는 Jest, `*.stories.tsx`는 Storybook Vitest addon, `e2e/*.spec.ts`는 Playwright가 실행한다.

### 우선순위

1. 기술 스택, 패키지 매니저와 프로젝트 구조 결정
2. 프로젝트 스캐폴딩과 로컬 실행 명령 통일
3. format, lint, typecheck, 단위·컴포넌트 테스트로 이어지는 빠른 내부 검증 루프
4. 도메인 스키마와 golden fixture를 사용한 핵심 규칙 검증
5. 로컬 개발, 컴포넌트 상태 확인과 테스트가 공유하는 API mock 경계
6. 브라우저 smoke test와 CI를 사용한 외부 검증 루프

### 완료 조건

- 새 환경에서 하나의 패키지 매니저로 의존성을 설치하고 프로젝트를 실행할 수 있다.
- 개발 서버와 공통 검증 절차를 저장소에 정의된 명령으로 실행할 수 있다.
- format, lint, typecheck와 단위·컴포넌트 테스트를 독립적으로 실행할 수 있다.
- 고정된 입력과 기대 결과로 핵심 도메인 규칙을 검증할 수 있다.
- 같은 API mock과 fixture를 로컬 개발, 컴포넌트 상태 확인과 테스트에서 재사용할 수 있다.
- 로딩, 빈 결과, 오류와 비활성 상태를 실제 외부 서비스 없이 확인할 수 있다.
- 최소 브라우저 smoke test와 CI가 공통 검증 명령을 실행한다.
- 기술 선택과 후속 구현 범위가 관련 Issue에 기록되어 있다.

### M1에서 하지 않는 일

- fixture 기반 대표 사용자 흐름 전체 구현
- 별도 API 애플리케이션과 서버 프레임워크 구성
- 실제 Steam 계정 연동과 사용자 인증
- 실제 리뷰 수집과 온라인 AI 분석 호출
- 데이터베이스와 운영 인프라 구축
- 애플리케이션 컨테이너와 PostgreSQL Compose 구성
- 8개 게임 전체의 실제 분석 데이터 작성

## M2: fixture 기반 핵심 사용자 흐름

fixture는 실제 API 대신 화면과 로직 검증에 사용하는 고정된 예시 데이터다. M2에서는 Steam 연동, 실제 리뷰 수집, 사용자 요청 시 온라인 AI 호출 없이 핵심 흐름을 완성한다.

### 우선순위

1. 로그인 없는 기본 리뷰 분석
2. 과거 게임 3개와 6개 요소 평가
3. 요소별 개인화 비교
4. 실제 리뷰 근거 확인
5. `구매 후보`, `보류`, `제외` 저장
6. 마이페이지 상태별 목록
7. 마이페이지의 과거 경험 평가 수정과 개인화 결과 재계산
8. 조건 미충족 사용자의 기본 분석 이용과 안내 흐름

### 완료 조건

- 사용자가 fixture 데이터만으로 기본 분석부터 구매 상태 저장까지 대표 흐름을 완료할 수 있다.
- 비교 기준 게임 3개에서 6개 요소를 모두 평가할 수 있다.
- 개인화 결과가 `맞을 근거`, `주의 신호`, `판단 불가`로 구분된다.
- 모든 노출 분석 결과에 fixture 리뷰 근거가 연결된다.
- 비교 기준 게임이 부족한 사용자는 기본 분석을 계속 이용할 수 있다.
- 과거 경험 평가를 수정하면 개인화 결과가 최신 입력을 반영한다.
- 종합 적합도 점수가 화면이나 로직에 포함되지 않는다.
- 대표 흐름과 주요 예외 흐름에 대한 E2E 테스트가 통과한다.

### M2에서 하지 않는 일

- 실제 Steam 계정 연동
- 실제 사용자 인증 방식 확정
- 실제 리뷰 수집과 갱신
- 온라인 AI 분석 호출
- 데이터베이스와 운영 인프라 확정
- 8개 게임 전체의 실제 분석 데이터 완성

## M3: MVP 안정화

### 목적

M2에서 구현한 대표 사용자 흐름의 오류와 빈 상태, 입력 검증, 접근성, 테스트와 UX를 보완해 사용 가능한 품질로 안정화한다.

### 완료 조건

- 대표 흐름과 주요 예외 흐름에서 발견된 치명적인 오류가 해결되어 있다.
- 사용자 입력의 유효성 검증과 복구 방법이 화면에 제공된다.
- 키보드 조작, 연결된 레이블과 자연스러운 포커스 이동을 확인할 수 있다.
- 자동 검증과 브라우저 검증이 안정적으로 통과한다.
- 핵심 사용자가 기본 분석과 개인화 비교 결과를 이해할 수 있다.

## M4: 베타 배포

### 목적

검증 가능한 베타 환경에 서비스를 배포하고 동작 상태와 사용자 피드백을 확인할 수 있는 운영 경계를 준비한다.

### 완료 조건

- 저장소의 검증 절차를 통과한 버전을 베타 환경에 배포할 수 있다.
- 배포 상태와 핵심 오류를 확인할 수 있다.
- 사용자 가치 검증 기준에 따른 피드백을 수집할 수 있다.
- 확인된 문제를 후속 Issue로 연결할 수 있다.

## fixture MVP 이후 범위 확장 후보

M2의 사용자 가치와 UX를 검증한 뒤 다음 작업의 세부 범위와 순서를 다시 확정한다. 다음 후보는 별도의 결정 없이 M3나 M4에 자동으로 포함하지 않는다.

1. Steam 라이브러리 연동과 수동 등록 경로
2. 실제 데이터 저장과 사용자별 구매 상태 관리
3. 리뷰 표본 수집, 구조화, 스키마 검증, 근거 연결 파이프라인
4. 8개 분석 대상 게임의 검수 데이터 적용
5. 소울라이크 경험자 3명 이상의 사용자 가치 검증

## 주요 위험과 대응 방향

| 위험 | 영향 | 대응 방향 |
| --- | --- | --- |
| Steam 라이브러리 비공개 또는 새 계정 | 자동 온보딩 실패 | Steam 등록 게임의 수동 등록 경로 제공 |
| 비교 기준 게임 부족 | 개인화 흐름 진입 불가 | 기본 분석은 공개하고 필요한 게임 수를 안내 |
| 리뷰 표본 편향 | 일부 의견을 전체 여론처럼 표현 | 전체 평가와 분석 표본을 분리하고 표본 정보를 공개 |
| 리뷰 구조화 오류 | 잘못된 특성을 사용자 취향과 비교 | 정해진 스키마, 실제 리뷰 근거, 핵심 게임 직접 검수 사용 |
| 근거 부족 또는 충돌 | 과도한 확신 제공 | `판단 불가`로 표시하고 종합 점수를 제공하지 않음 |
| 과거 경험 평가 수정 | 이전 취향을 반영한 결과가 남음 | 개인화 결과를 최신 입력으로 다시 계산 |
| 지원 게임 범위 확대 | 검수 품질 저하와 일정 지연 | 8개 게임으로 시작하고 검증 후 확대 |
| 외부 데이터 출처 확대 | 크롤링·정규화·유지보수 증가 | MVP는 Steam 공식 정보와 Steam 리뷰로 제한 |

## 검증 순서

1. 문서에서 제품 범위와 용어의 일관성을 확인한다.
2. fixture로 대표 사용자 흐름과 예외 흐름을 E2E 테스트한다.
3. 핵심 사용자에게 기본 분석과 개인화 비교의 이해 가능성을 확인한다.
4. 제품 가치가 확인된 뒤 Steam과 실제 리뷰 파이프라인을 연결한다.
